## Scope — what this skill assumes about the app

This app was generated by `@ronas-it/nx-generators`'s `next-app` generator, so
`libs/<app>/shared/ui/ui-kit/src/lib` exists. Beyond that, don't assume a fixed shape — read what's
actually in that directory before changing anything; existing apps in this repo show real variance
(e.g. components living flat under `src/lib/<name>/component.tsx`, or nested under
`src/lib/components/<name>/component.tsx` on other platforms). If more than one app under `apps/`
has a matching `ui-kit`, ask the user which one this run targets before doing anything — don't
guess.

## Phase 0 — UI library detection (required, do this first)

Before touching any component, determine which UI library the app's `ui-kit` actually builds on —
implementation strategy differs completely depending on the answer:

1. Check `libs/<app>/shared/ui/ui-kit/src/lib/theme.tsx` (or `theme.ts`) for existence. If it
   exists, read it — this app uses **Mantine**, and per the `configure-mantine-theme` skill's own
   scope check, that file's `createTheme(...)` call is where styling lives.
2. If no `theme.tsx` exists, check the app's `package.json` / the `ui-kit` lib's dependencies for
   another known UI library (Chakra UI, MUI, Ant Design, etc.), and skim a couple of existing
   component files under `src/lib/` for their imports to confirm what they're actually built on
   (plain CSS modules + native elements is also a valid answer — e.g. this repo's `Icon` component
   has no UI-library dependency at all).
3. Report which library you found before proceeding, and adapt the phases below accordingly:
   - **Mantine** — read [references/mantine.md](references/mantine.md) in full before Phase 2. It
     covers the exact implementation pattern (a `classNames` picker + a colocated
     `theme.module.scss`, not a custom `variantColorResolver` or `vars`/`styles` functions) verified
     end-to-end against this design system's own production codebase, plus specific pitfalls (an
     inline-style trap that silently disables `:focus`/`:hover`/`[data-error]` reactivity) that have
     already produced plausible-but-wrong theming code once. Don't skip it and reconstruct the
     approach from Mantine's docs alone — the naive approach looks reasonable and is wrong in ways
     that only show up on hover/press/focus, not in a static screenshot.
   - **A different component library** — the same overall approach applies (find that library's
     own per-component theming API — e.g. MUI's `createTheme({ components: { MuiButton: {...} } })`,
     Chakra's `extendTheme`'s `components` key — and extend the Button/TextInput/Checkbox entry
     there instead of writing new component markup), but this skill's step-by-step detail below is
     Mantine-specific; adapt the intent, not the literal Mantine API calls.
   - **No UI library** — there's no shared theme file to extend; each phase below instead means
     building/updating the component's own `component.tsx` + `component.module.scss`, following the
     conventions already visible in this `ui-kit`'s other from-scratch components.

## Phase 1 — inputs and Figma access

Skip this whole phase if you were handed a Figma link/access and a target `<app>` already (i.e.
you're running as part of `import-figma-ui`) — go straight to Phase 0's detection if not already
done, then Phase 2.

1. **Figma link.** If the user didn't already give you a link to the Figma UI-kit design page, ask
   for one — you cannot proceed without it.
2. **Target app.** Resolve `<app>` per the Scope section above.
3. **Figma tooling.** The required preflight above should already have provided a compatible tool.
   Locate the three top-level blocks on the page behind the link: **"Buttons"**, **"Inputs"**, and
   **"Checkboxes and Radio Buttons"**. Note their node IDs — later phases each drill into one.
4. Also confirm `libs/<app>/shared/ui/styles/_variables.scss` exists and read it — every color,
   size, and spacing value the phases below write into `theme.tsx` must reference a `var(--...)`
   token from this file, never a hardcoded literal, the same rule `configure-mantine-theme` follows.
   If a state color a component needs (e.g. a button's hover/pressed/disabled fill, an input's error
   border) isn't in `_variables.scss` yet, read
   [`../import-figma-vars/references/colors.md`](../import-figma-vars/references/colors.md) and add
   that one missing token the same careful way (SVG export, not a screenshot guess) rather than
   inventing a value or re-running the whole `import-figma-vars` phase for one row.

## Honor the user's own wishes for this run

A narrower request ("only do buttons", "skip checkboxes") means run only the corresponding
phase(s) below. If nothing is specified, run all three.

## Phase 2 — Buttons → `AppButton`

1. Inside the "Buttons" block, read every variant (e.g. Primary/Secondary/Outline/Text/Danger),
   size, and state (default/hover/pressed/disabled/loading) shown. Screenshot the block if the
   variants aren't obvious from layer names alone — don't guess a variant's visual treatment from
   its name. Pay particular attention to whether hover/pressed change the _background_ or just the
   _border/text_ color for non-filled variants — both are real, common Figma choices, and guessing
   wrong here is the single most common mistake (see references/mantine.md).
2. Find the component that wraps Mantine's `Button` in this `ui-kit` (commonly `AppButton` at
   `src/lib/button/component.tsx` — read what's actually there rather than assuming the name).
   - **If it exists**, leave its own logic (loading state, polymorphism, etc.) untouched — this
     phase only concerns visual styling.
   - **If no such wrapper exists yet**, create one following the pattern of this `ui-kit`'s other
     wrapper components (a thin function/`polymorphic` wrapper around Mantine's `Button` that
     forwards props), then export it from the lib's index file.
3. Implement the styling per [references/mantine.md](references/mantine.md) — a `classNames` picker
   in `theme.tsx` plus the actual rules in `theme.module.scss`, not a custom `variantColorResolver`
   or `vars`/`styles` functions. Map each Figma variant onto Mantine's existing `variant` prop values
   (`filled`, `outline`, `subtle`, `transparent`, …) wherever the visual treatment matches. Reference
   `_variables.scss` tokens for every color/size, same rule as Phase 1.

## Phase 3 — Inputs → `TextInput`

1. Inside the "Inputs" block, read every state (default/focused/filled/error/disabled) and any
   size variants shown. Check specifically whether the border is visible in the default/filled
   states or only appears on focus/error — that distinction drove a real bug once (see
   references/mantine.md's inline-style trap).
2. Find the component that wraps Mantine's `TextInput` (commonly `FormTextInput` at
   `src/lib/form-text-input/component.tsx`) — same existence check as Phase 2: leave its
   field-binding logic untouched, this phase is styling only.
3. Implement the styling per [references/mantine.md](references/mantine.md) — border color per
   state (default/focus/error/disabled), error-state color (reusing whatever error/danger token
   `_variables.scss` already defines from prior imports, adding it via the Phase 1 process if it's
   missing), and font-size/line-height/height. If the default size looks wrong, check the
   component's own built-in `size` default before adding a manual override.

## Phase 4 — Checkboxes → `Checkbox`

1. Inside the "Checkboxes and Radio Buttons" block, read only the checkbox rows (not the radio
   button rows — Radio Button is out of scope for this run unless the user explicitly asked for
   it; note in the finishing summary that the block also contained radio buttons left unimplemented).
2. Find the component that wraps Mantine's `Checkbox` (commonly `FormCheckbox` at
   `src/lib/form-checkbox/component.tsx`) — same existence check as Phase 2.
3. Implement the styling per [references/mantine.md](references/mantine.md) — checked/unchecked/
   indeterminate fill and border colors, size, border-radius. A single accent color usually needs
   no more than `defaultProps.color`; only reach for the `classNames`/`theme.module.scss` pattern if
   checkboxes actually vary by color/type in this Figma file.

## Verify

1. `theme.tsx` is TypeScript — run `npm run lint` (or the repo's equivalent `tsc`/`eslint` script,
   check `package.json` if the name differs) from the repo root and fix anything it flags.
2. **Visually confirm before finishing.** Render each implemented component's variants/states on a
   throwaway page/route, screenshot it, and compare side-by-side against the Figma block
   screenshots from Phases 2–4. **Delete the throwaway page afterward, and confirm it's actually
   gone** (e.g. `git status` shows nothing left under the route you added) **before reporting this
   phase done** — don't just state the intent to delete it in the finishing summary.
3. **A screenshot can't show `:hover`/`:active`/`:focus-visible`.** For any state that needs a live
   cursor, confirm the CSS is wired correctly by fetching the running dev server's compiled CSS
   bundle and grepping it for the expected rule, and fetching the rendered HTML to confirm the DOM
   elements actually carry the classes/attributes that rule depends on — see
   references/mantine.md's verification section for the exact steps (Mantine apps only; for other
   UI libraries, adapt the intent). This confirms the mechanism is connected; still ask the user to
   spot-check the live interactive behavior in a real browser before finishing.
