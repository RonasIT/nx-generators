# Update dependencies (example apps + generator plugin)

This repository ships **generators** (`plugin/src`) that scaffold apps with hardcoded
dependency versions, and it also contains **example apps** (`apps/mobile`, `apps/web`) that are
generated by those same generators and used as a live testing ground. Updating dependencies here
always has two halves: update the real apps, then teach the generators to produce the same
versions for anyone who runs them in the future. Skipping the second half is the most common way
this task goes wrong — a generator that still emits last month's versions.

This file is written as plain instructions (shell commands + file edits) so it works with any
coding agent, not just one particular tool. It is the **single source of truth** for this task —
`.claude/skills/update-dependencies/SKILL.md` (Claude Code),
`.agents/skills/update-dependencies/SKILL.md` (Codex CLI),
`.github/prompts/update-dependencies.prompt.md` (GitHub Copilot),
`.windsurf/workflows/update-dependencies.md` (Windsurf), and
`.cursor/commands/update-dependencies.md` (Cursor) are thin adapters that just point here so
colleagues can run this as a slash command (or, for Codex, an auto-matched skill) from their own
tool. If you change the steps below, those files don't need edits; if you rename/move this file,
update the paths in all five.

Read the whole file before starting; the phases build on each other and some decisions in Phase 1
depend on what kind of update this is.

## Ground truth about this repo (verified, don't re-derive)

- Root `package.json` is an npm-workspaces root (`workspaces: ["apps/*", "plugin/*"]`) and holds
  the dependencies for **`apps/web`** directly (that app has no `package.json` of its own).
- `apps/mobile/package.json` holds the dependencies for the Expo/React Native example app.
- `plugin/src/shared/dependencies.ts` is the **single source of truth inside the generators** for
  every hardcoded version they write into a freshly generated app's `package.json`. It exports
  two objects, `dependencies` and `devDependencies`, keyed by generator/feature name
  (`expo-app`, `next-app`, `api-client`, `auth`, `next-auth`, `rn-styles`, `ui-kit`, `store`,
  `form`, `sentry.expo`, `sentry.next`, `nuqs`, `code-checks`, `repo-config`). Every generator
  (`plugin/src/generators/**/generator.ts`, `plugin/src/shared/generators/**/generator.ts`)
  imports from this file and calls Nx's `addDependenciesToPackageJson`. **There is no other place
  in `plugin/src` with a hardcoded version** — grep for `export const dependencies` if in doubt.
- `plugin/package.json` has its own, separate `dependencies`/`devDependencies` — these are the
  runtime deps of the generator code itself (`ts-morph`, `lodash`, `tslib`, `@nx/devkit`,
  `typescript`), not something it hands out to consumers. They should track the same versions used
  at the repo root, but are not part of `dependencies.ts`.
- `.npmrc` sets `min-release-age=3` (and `engine-strict=true`) — don't install a package version
  published more recently than that, to avoid pulling a just-published (and potentially
  compromised) release. `npm-check-updates` honors this automatically, see Phase 1c.
- A helper script, `tools/scripts/check-generator-dependencies.mjs` (run via
  `npm run deps:check-generators`), diffs every version in `dependencies.ts` against the current
  root/`apps/mobile` package.json and prints a mismatch table. It's read-only. Use it in Phase 2
  instead of eyeballing the diff by hand.

## Decide what kind of update this is first

These four cases need different tooling and should generally be done in this order, since Nx,
Expo, and Next.js upgrades manage their own peer versions/breaking changes and you don't want a
plain dependency bump to fight with them:

1. **Nx itself has a newer version** (`nx`, `@nx/*` in root `package.json`) → Phase 1a (`nx
migrate`).
2. **A new Expo SDK is out** (`expo` in `apps/mobile/package.json` / root) → Phase 1b
   (`expo-upgrade` skill).
3. **A new Next.js major/minor is out** (`next` in root `package.json`, which is where
   `apps/web`'s dependencies live) → Phase 1c (`@next/codemod`).
4. **Everything else** (routine minor/patch bumps across the board) → Phase 1d
   (`npm-check-updates`).

If this is a routine update and none of Nx, Expo, or Next.js have a new major out, skip straight
to 1d.

## Phase 1 — update the example apps

### 1a. Nx workspace upgrade (`nx migrate`)

Follow <https://nx.dev/docs/features/automate-updating-dependencies>. Concretely:

```sh
npx nx migrate latest      # or `npx nx migrate nx@<version>` to target a specific version
```

This updates `nx`/`@nx/*` versions in `package.json` and, if any generator needs to run against
this workspace's code for the new version, writes `migrations.json` at the repo root.

Run the migrations **programmatically** — this is a hard requirement from the maintainer, not
just a preference: do not hand-edit files to satisfy a migration note, and do not have an AI
agent "interpret and apply" a migration manually, when Nx can run it as code:

```sh
npm install
npx nx migrate --run-migrations
```

Only fall back to manually reading a migration's description and editing files by hand for a
migration that fails to run automatically or that explicitly requires a manual step (some
migration notes are informational only). After migrations succeed, delete `migrations.json` (it's
scratch state, not something to commit) and run `npm run lint` and `npx nx test nx-generators` to
confirm nothing broke.

### 1b. Expo SDK upgrade (`expo-upgrade` skill)

Prefer Expo's own official upgrade skill over ad-hoc changes — it encodes per-version breaking
changes (New Architecture, deprecated packages, etc.) that are easy to miss by hand.

1. **Check whether it's already available** in your current agent environment:
   - Claude Code: look for a skill named `expo-upgrade` (often shown as `expo:expo-upgrade`) in
     your available skills, or an Expo MCP/plugin already connected.
   - Any other agent: check whether an `expo-upgrade` (sometimes `upgrading-expo`) skill/`SKILL.md`
     is already installed wherever your tooling keeps skills.
2. **If it's available, use it** to drive the upgrade from the **repo root** — not `apps/mobile` —
   since `expo` and its adjacent packages are also declared in the root `package.json`. Then copy
   the resulting versions by hand into the matching packages in `apps/mobile/package.json` and run
   `npm install` from the root so both `package.json` files and the lockfile agree.
3. **If it's not available, install it** — but confirm with the user first, since this changes
   their agent environment/config, not just this repo:
   - Claude Code: `/plugin install expo@claude-plugins-official` (adds the official Expo plugin,
     which bundles the `expo-upgrade` skill).
   - Generic agents that support the community skills installer: `npx skills@latest add expo/skills
--skill expo-upgrade` (verify current syntax at <https://docs.expo.dev/skills/> — this
     tooling is young and may have changed).
4. **If installing isn't possible either**, fall back to a manual upgrade: read the changelog for
   the target SDK version (<https://expo.dev/changelog> or the release notes on
   <https://github.com/expo/expo/releases>), then run the install commands from the **repo root**
   — not `cd apps/mobile` — since `expo` and its adjacent packages are also declared in the root
   `package.json`:
   ```sh
   npx expo install expo@latest    # or a specific SDK, e.g. expo@^58.0.0
   npx expo install --fix
   ```
   Copy each resulting version by hand into the matching package in `apps/mobile/package.json`,
   then reinstall from the root so both `package.json` files and the lockfile agree:
   ```sh
   npm install
   ```
   Finish with `npx expo-doctor` from inside `apps/mobile` (it validates that specific project, so
   it's the one command here that must run in the app directory). Address every breaking change
   called out in the changelog by hand, then re-run `expo-doctor` until it's clean.

Either way, finish by reconciling `apps/mobile/package.json` against the root `package.json` for
any Expo-managed package that's also listed at the root (e.g. `expo`, `expo-router`,
`react-native`, `react`) — they should stay in lockstep.

### 1c. Next.js upgrade (`@next/codemod`)

Prefer Next.js's own official codemod CLI over a plain version bump for a major/minor jump — it
bumps the version _and_ runs the automated transforms for that version's breaking changes (e.g.
renamed APIs, config shape changes), which are easy to miss doing this by hand.

`apps/web` has no `package.json` of its own — `next`, `eslint-config-next`, and `next-intl` all
live in the root `package.json` — but the app's actual source (the `app/` router tree the codemod
transforms need to walk) lives under `apps/web`. Run from the **repo root** so the CLI edits the
right `package.json`:

```sh
npx @next/codemod@canary upgrade latest    # or a specific target, e.g. `upgrade 16.x.x`
```

The CLI is interactive: it confirms the target version, updates `next` in the root `package.json`,
runs the install, then walks you through whichever codemods apply between your current version and
the target. When it asks which directory to transform, point it at `apps/web` (the tool defaults
to cwd, which at the repo root has no `app`/`pages` directory of its own — don't let it silently
transform nothing). If a step doesn't prompt for a path and instead just reports "no pages/app
directory found," re-run that specific codemod directly against the app directory, e.g.:

```sh
npx @next/codemod@canary <transform-name> apps/web
```

(`<transform-name>` is whatever the interactive run named as the codemod it skipped — check
<https://nextjs.org/docs/app/guides/upgrading/codemods> for the current list and syntax if it's
unclear, since exact transform names change between Next.js releases.)

After the codemod run, reconcile `eslint-config-next` in the root `package.json` to match the new
`next` version by hand if the CLI didn't already bump it — they're released in lockstep and should
carry the same version number. Then run `npm install` and confirm `apps/web` still builds and
lints (`npx nx build web`, `npx nx lint web`) before moving on.

### 1d. Routine updates (`npm-check-updates`)

Use `npm-check-updates` (`ncu`) to bump everything else.

**Note:** invoke it as `npm-check-updates`, not the bare `ncu` binary — `npx ncu` can resolve to
an unrelated package of that exact name on the npm registry.

```sh
npx --yes npm-check-updates --root --workspaces --reject '/^(@nx\/.*|nx)$/'
```

Run it once without `-u` first (as above) to review the plan, then re-run with `-u` appended to
actually write the new versions:

```sh
npx --yes npm-check-updates --root --workspaces --reject '/^(@nx\/.*|nx)$/' -u
```

- `min-release-age` from `.npmrc` is picked up automatically — `ncu` prints `Using min-release-age
from .npmrc: 3 days` and holds back anything newer (shown as `[cooldown] x.y.z` in the dry run,
  meaning a newer version exists but isn't old enough yet). No extra flag needed; only pass
  `--cooldown <n>` explicitly if you want to override that value for this run.
- `--root --workspaces` covers the root `package.json` (→ `apps/web`'s dependencies, since it has
  no package.json of its own) and every workspace package.json (`apps/mobile`, `plugin`) in one
  pass.
- `--reject '/^(@nx\/.*|nx)$/'` excludes Nx packages — those are handled by `nx migrate` (Phase
  1a) since they need codemods, not just a version bump. (`--reject` takes one regex, not a
  comma-list of regexes — combine multiple patterns into one with `|` as shown.)
- If Phase 1b (Expo upgrade) already ran, either exclude `expo`/`expo-*` here too (`--reject`) or
  re-run `npx expo install --fix` afterwards to make sure `ncu` didn't push an Expo package outside
  the SDK's supported range.
- If Phase 1c (Next.js codemod) already ran, exclude `next`/`eslint-config-next` here too
  (`--reject`) so `ncu` doesn't bump them past the version the codemods were written for.
- `ncu -u` preserves each package's existing range operator (`^`, `~`, exact) while bumping the
  version — it will not, by itself, change `~19.2.7` into `^19.2.7` or vice versa.

Then install and let the existing workspace tooling reconcile any version drift between the
root/`apps/mobile`/`plugin` package.json files:

```sh
npm install
npm run deps:sync
```

## Phase 2 — propagate the changes into the generators

This is the step most likely to be forgotten. Every version you just changed in `apps/mobile` or
the root `package.json` that's also mirrored in `plugin/src/shared/dependencies.ts` needs to be
updated there too, or every future run of the generators will scaffold outdated dependencies.

1. Run the diff helper:
   ```sh
   npm run deps:check-generators
   ```
   It prints every package where `dependencies.ts` and the workspace disagree, plus anything it
   couldn't find in the workspace at all (flagged `CHECK MANUALLY` — e.g. a package only used by
   `apps/web` indirectly, or a genuinely generator-only pin like a Sentry SDK version that isn't
   installed anywhere in this workspace).
2. For each `MISMATCH` row, edit `plugin/src/shared/dependencies.ts` and update just the version
   number, **keeping the existing range operator that's already in that file** (it sometimes
   deliberately differs from the workspace's own pin — e.g. the workspace may pin an exact version
   while `dependencies.ts` intentionally hands consumers a `~` range — so don't blindly copy the
   workspace's operator over).
3. For each `CHECK MANUALLY` row, decide by hand: if it's a real package this workspace should also
   depend on, add/update it there and re-run the check; if it's intentionally generator-only,
   leave it and update it from the package's own changelog/registry page instead.
4. Also review `plugin/package.json`'s own `dependencies`/`devDependencies`
   (`@nx/devkit`, `ts-morph`, `lodash`, `tslib`, `typescript`) against the root `package.json` —
   these aren't covered by `dependencies.ts` or the check script, since they're the plugin's own
   runtime/dev dependencies, not something it injects into consumers.
5. Update `plugin/generators.json` and any generator option docs/README sections if a dependency
   bump changed available options (e.g. a new major requires a new flag) — this is rare for a pure
   version bump, but check if Phase 1a/1b involved breaking changes.
6. Re-run `npm run deps:check-generators` until it reports no mismatches (`CHECK MANUALLY` rows
   for legitimately generator-only packages are fine to leave).

## Phase 3 — test the package before publishing

1. **Automated tests:**
   ```sh
   npx nx test nx-generators   # unit tests for the generators
   npm run test:e2e            # builds, publishes via Yalc, scaffolds a throwaway workspace,
                                # runs repo-config/code-checks/expo-app/next-app, lints the result
   npm run lint                # tsc + eslint at the repo root
   ```
2. Do **not** publish the plugin as part of this skill — not `npm run release` (with or without
   `--tag=alpha`), not a manual `yalc publish`, no GitHub release, tags, or push to a shared branch.
   Those are publish/ship steps and out of scope for "update dependencies" unless explicitly asked
   for; verifying the generators against the updated dependencies is left to the user by hand (see
   "Finishing up" below).

## Finishing up

When all phases are done, print a short summary for the user: what kind of update this was (1a/1b/
1c, or a combination), the key version changes (e.g. Nx version, Expo SDK version, notable major
bumps), what got propagated into `dependencies.ts`/`plugin/package.json` in Phase 2, and the result
of the automated checks in Phase 3.

If everything above succeeded, close by asking the user to verify by hand what this skill cannot
verify for itself:

- Manually run and click through `apps/mobile` and `apps/web`.
- Manually verify the plugin's generators still work as expected with the updated dependencies
  (e.g. by running them against a real or throwaway test project), beyond what `test:e2e` already
  covers automatically.

## Summary of what to run, in order

```sh
# Phase 1 — pick whichever of 1a/1b/1c apply, always finish with 1d
npx nx migrate latest && npm install && npx nx migrate --run-migrations   # 1a, if Nx has an update
# ...expo-upgrade skill or manual `expo install`/`expo-doctor` flow...     # 1b, if Expo SDK bumped
npx @next/codemod@canary upgrade latest                                   # 1c, if Next.js has a new major/minor
npx --yes npm-check-updates --root --workspaces --reject '/^(@nx\/.*|nx)$/' -u   # respects .npmrc min-release-age automatically
npm install && npm run deps:sync

# Phase 2 — propagate into the generators
npm run deps:check-generators   # then edit plugin/src/shared/dependencies.ts + plugin/package.json

# Phase 3 — test the package
npx nx test nx-generators && npm run test:e2e && npm run lint
```
